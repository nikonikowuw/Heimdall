# 跨层思考指南

> **用途**：动手实现之前，先把数据在各层之间怎么流动想清楚。

---

## 问题所在

**大多数 bug 发生在层与层的边界上**，而不是层的内部。

常见的跨层 bug：

- API 返回格式 A，前端期望格式 B
- 数据库存 X，服务层转成 Y，中间丢了信息
- 多个层各自实现了同一套逻辑，行为不一致

Heimdall 的层特别多 —— C++ SDK、Rust 各 crate、HTTP/WS、TypeScript 前端，中间还跨了语言和进程边界。**跨语言的边界编译器帮不上忙**，只能靠约定和测试。

---

## 实现跨层功能之前

### 第一步：画出数据流

把数据怎么走画出来：

```
来源 → 转换 → 存储 → 读取 → 转换 → 展示
```

对每一个箭头问：

- 数据此时是什么格式？
- 可能出什么错？
- 谁负责校验？

### 第二步：识别边界

| 边界 | 常见问题 |
|------|---------|
| C++ SDK ↔ Rust FFI | 内存所有权、错误码转换、结构体布局 |
| `media` ↔ `infer` | 帧格式、buffer 生命周期、平台句柄类型 |
| `pipeline` ↔ `db` | 领域类型与 entity 的映射、时间戳单位 |
| Rust ↔ TypeScript | 序列化命名、`Option` vs `null`、时间戳表示 |
| 组件 ↔ 组件 | props 形状变更 |

### 第三步：定义契约

对每个边界：

- 输入格式**具体**是什么？
- 输出格式**具体**是什么？
- 可能发生哪些错误？

---

## 常见的跨层错误

### 错误 1：隐式的格式假设

**差**：不确认就假设时间格式

**好**：在边界上做显式转换。Heimdall 的约定是：**系统内部统一 Unix 毫秒整数**，只在 UI 展示时转人类可读格式。见 [../backend/database-guidelines.md](../backend/database-guidelines.md)。

### 错误 2：校验分散在多层

**差**：同一件事在多个层各校验一遍

**好**：在入口处校验一次。Heimdall 的入口是 HTTP handler 边界和配置加载 —— 过了这两处，内部就当数据是可信的。

### 错误 3：抽象泄漏

**差**：前端组件知道数据库 schema；`pipeline` 知道用的是哪个 NPU

**好**：每一层只认识相邻的层。**平台差异不允许泄漏出 `infer` / `media`**，见 [../backend/inference-backends.md](../backend/inference-backends.md)。

### 错误 4：每个消费方各自解析同一份 payload

**差**：多处就地断言事件字段：

```typescript
const cameraId = (msg as { cameraId?: string }).cameraId
const label = (msg as { label?: string }).label
```

看起来是局部代码，实际上每个消费方都私有了一份事件契约。下次字段变更会改到一个、漏掉另一个。

**好**：在边界处解码一次，然后导出带类型的投影：

```typescript
if (!isEventCreated(msg)) return
onEvent(msg.payload)
```

**规则**：对于 WebSocket 消息、JSON 流、配置文件，下面这些东西必须有唯一所有者：

- 事件 / payload 的类型定义
- 从 `unknown` 收窄的类型守卫与归一化
- 供 UI 使用的元数据投影
- 从真相源重放状态的 reducer

渲染代码可以格式化字段，但**不能重新定义 payload 契约**。

## 跨层功能检查清单

实现前：

- [ ] 完整画出了数据流
- [ ] 识别出所有层边界
- [ ] 定义了每个边界上的格式
- [ ] 确定了在哪一层做校验

实现后：

- [ ] 用边界值测过（null、空、非法值）
- [ ] 验证了每个边界的错误处理
- [ ] 确认数据往返一趟没有丢失或变形
- [ ] 确认消费方 import 的是共享解码器，而不是就地断言
- [ ] 确认派生状态指回源事件标识（`id`、`seq`），而不是另造一个游标

## 新增事件类型时（Heimdall 特有）

一个事件从产生到显示要穿过全部层：

```
推理输出 → 事件判定 → SQLite 写入 → API 查询 → WS 推送 → 前端 store → 渲染
```

### 检查清单：新增事件类型或字段后

- [ ] `types` 里加了事件类型定义（枚举变体，不是字符串）
- [ ] `db` 里 entity 和 migration 跟上了（**migration 只增不改**）
- [ ] `api` 里 DTO 和 `From` 实现跟上了
- [ ] WebSocket 消息的联合类型加了新变体
- [ ] 前端 `src/types/api.ts` 同步了字段
- [ ] 前端 `switch` 的 `never` 穷尽检查通过了（会在编译期报错提醒你）
- [ ] 事件 ID 的分配只发生在一个地方（不要让前端和后端各造一份 ID）
- [ ] 历史分页拉取和实时推送的合并逻辑处理了去重

**最容易漏的是最后两条**。实时推送和分页历史是两条独立的路径，同一个事件可能从两边都到达前端 —— 不按 ID 去重就会出现重复条目。

## 跨语言边界的特殊警告

Rust ↔ TypeScript 之间**没有编译器保护**。后端改了字段名，前端要到运行时才发现。

缓解手段：

- 后端 DTO 集中在 `crates/api/src/dto/`，前端类型集中在 `src/types/api.ts`。**两边都集中**，改的时候至少是"改两个文件"而不是"改二十处"
- `Option<T>` 序列化成 `null` 而非 `undefined`，前端类型要写 `T | null`
- 改任何 DTO 字段时，`rg` 一遍前端仓库确认没有遗漏
- 长期方案是从后端生成 TypeScript 类型，见 [../frontend/type-safety.md](../frontend/type-safety.md) 的待验证事项

Rust ↔ C++ 之间同样没有保护，且后果更严重（是 UB 而不是白屏）。见 [../backend/ffi-guidelines.md](../backend/ffi-guidelines.md)。

## 什么时候该写流程文档

在下列情况下，把数据流写进 `design.md`：

- 功能横跨 3 层以上
- 涉及跨语言边界
- 数据格式复杂（尤其涉及帧格式、坐标系转换）
- 这块以前出过 bug

---

## 坐标系是 Heimdall 最危险的跨层契约

一个检测框的坐标要经过：

```
原始分辨率 → 预处理缩放 + letterbox padding → 模型输出（归一化或像素）
    → 后处理还原到原始分辨率 → API 输出 → 前端按百分比渲染到播放器上
```

每一步都可能出错，且**错误表现是"框偏一点点"，肉眼难发现、日志看不出、测试如果只测 happy path 也发现不了**。

### 检查清单：改动任何坐标相关代码后

- [ ] 缩放与还原是严格的互逆运算，且共用同一组参数
- [ ] 测了非整除的分辨率（1920×1080 → 640×640）
- [ ] 测了贴边的框（坐标为 0 或等于宽高）
- [ ] 确认了模型输出是归一化坐标还是像素坐标（不同模型不一样，写进 `manifest.toml`）
- [ ] 前端用百分比而非像素定位叠加层，见 [../frontend/styling-guidelines.md](../frontend/styling-guidelines.md)
- [ ] 三个平台后端的坐标输出格式一致（量化可能引入偏差，但格式必须相同）

## 配置字段的跨层一致性

一个配置项（例如"检测阈值"）通常同时存在于：

```
配置文件 → Rust Config 结构 → 管线运行时参数 → API 返回给前端 → 设置页表单 → 写回配置文件
```

### 检查清单：新增配置字段后

- [ ] Rust `Config` 结构加了字段，并有合理的 `#[serde(default)]`
- [ ] 老配置文件在没有这个字段时仍能加载（**向后兼容是硬要求**，设备上的配置不会自动升级）
- [ ] 校验规则写在一处（不要 Rust 校验一遍、前端表单再校验一套不同的规则）
- [ ] 热重载路径也覆盖了这个字段（如果配置支持热重载）
- [ ] 前端设置页的表单类型与后端 DTO 对齐
