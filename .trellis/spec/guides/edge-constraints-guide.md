# 边缘资源约束思考指南

> **目的**：Argus 跑在 RK3568 这类设备上，不是跑在服务器上。写代码前用这份清单过一遍，避免写出在开发机上跑得好、上设备就崩的代码。

> ⚠️ **状态：立项约定（尚未经代码验证）**
> 具体数值阈值需在真机基线测试后回填。

---

## 为什么需要这份指南

服务器后端的默认习惯在边缘设备上大多是错的：

| 服务器上的习惯 | 在 Argus 上的后果 |
|---------------|------------------|
| "先 clone 一份，安全" | 每帧 1080p RGB 拷贝 = 6 MB，8 路 15fps = 720 MB/s 内存带宽 |
| "先全读进内存再处理" | 一段 10 分钟录像直接把可用内存吃光 |
| "日志打详细点方便排查" | 帧级日志把 eMMC 写穿 |
| "用 tokio 就完事了" | 在 async 任务里调阻塞 FFI，把整个 runtime 卡死 |
| "加个缓存，快" | 无上界缓存 = 运行三天后 OOM |
| "失败了重试就行" | 无退避重试把摄像头和 NPU 一起打爆 |

## 写代码前必答的四个问题

### 1. 这段代码在每帧执行吗？

如果是，它的开销要乘以 `路数 × 帧率`。

- 8 路 × 15fps = **每秒 120 次**
- 一次多分配 1 KB，就是每秒 120 KB 的分配压力
- 一次多一个 `format!()`，就是每秒 120 次堆分配

**规则**：每帧路径上禁止 `format!`、`to_string()`、`Vec::new()` 等隐式分配。缓冲区在管线启动时预分配并复用。

### 2. 这块内存的上界是多少？

任何队列、缓存、批处理容器都必须有明确上界。

- 帧队列：**必须有界**，满了丢最旧的帧（丢帧优于 OOM）
- 事件缓存：按条数或字节数封顶
- 录像片段缓冲：按时长封顶

**反模式**：`tokio::sync::mpsc::unbounded_channel()` 用在帧路径上。消费者一慢，内存就无上界增长。

### 3. 这次写盘会发生多少次？

嵌入式设备普遍是 eMMC 或 SD 卡，写寿命有限，写放大是真实故障源。

- 事件元数据写 SQLite：可以，但要批量提交，不要一条一个事务
- 帧级日志写文件：**禁止**
- 快照/录像：必须有保留策略（按容量或天数自动清理），落地前就要写好
- **磁盘高低水位防护（Watermark Policy）**：写入录像和快照前必须检查分区剩余容量。低于低水位（如 10%）立即触发加速清理；低于极危水位（如 5%）熔断停写，严禁把 rootfs 写爆导致文件系统只读挂载。

### 4. 这个调用会阻塞多久？

平台 SDK（RKNN、AscendCL、VideoToolbox）几乎全是同步阻塞接口，单次调用几十到几百毫秒。

- 阻塞调用**绝不能**出现在 async 任务里，见 [backend/concurrency-guidelines.md](../backend/concurrency-guidelines.md)
- 阻塞调用要有超时，SDK 卡死时能被检测到

## 资源预算的思考方式

新增功能时，先在 PR 描述或 design.md 里写清楚这三行：

```
内存增量：  每路 + ___ MB，8 路 + ___ MB
CPU 增量：  每帧 + ___ ms，占用 ___ %
存储增量：  每天 + ___ MB
```

写不出来说明你还不知道这段代码的开销 —— 那就先测，别先写。

## 常见踩坑清单

- [ ] 用 `Vec<u8>` 传帧数据 → 应该传平台原生 buffer 句柄，见 [backend/media-pipeline.md](../backend/media-pipeline.md)
- [ ] 忽略硬件解码的行/列步长（Stride）对齐 → 导致图像出现绿条、花屏或内存越界
- [ ] CPU 读 DMA-BUF 前未调用 `DMA_BUF_IOCTL_SYNC` → 读到过期的 CPU 脏 Cache
- [ ] 在帧通道上调用阻塞 `send()` → 反向卡死硬件解码线程
- [ ] 在 `Drop` 里做阻塞清理 → 设备关机时会挂住
- [ ] 忘记释放 DMA-BUF fd / CVPixelBuffer → 句柄泄漏，几小时后耗尽
- [ ] 模型每次推理都重新加载 → 加载耗时是推理的几十倍，模型必须常驻
- [ ] 用 `std::thread::spawn` 无上限开线程 → 每路摄像头固定线程数，见 concurrency 规范
- [ ] SQLite 未开 WAL → 读写互斥，事件写入阻塞 API 查询
- [ ] 写入快照/录像前未检查存储水位 → 把设备存储撑爆
- [ ] 前端轮询接口拉全量事件列表 → 走 WebSocket 增量推送
- [ ] 前端用频繁更新的 DOM 元素渲染检测框 → 触发每秒上千次重排卡死页面，改用 Canvas 2D

## 降级优于崩溃

设备无人值守，任何单点故障都不应该拖垮整个系统：

- 一路摄像头断流 → 只有这一路降级重连，其它路正常
- NPU 推理失败 → 该帧跳过并计数，不要 panic
- 磁盘写满 → 触发保留策略清理，清理不出空间就停止录像但保持 API 可用
- 模型加载失败 → 启动时明确报错退出（这个要 fail fast），运行中失败则该路停用
- 进程心跳与自愈 → 接入 systemd watchdog（`sd_notify`），在内部工作线程发生不可逆死锁时由系统自动重启进程

**判断标准**：能局部降级的绝不整体退出；启动期配置/模型错误则必须 fail fast，不要带病运行。
