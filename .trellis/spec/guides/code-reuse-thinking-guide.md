# 代码复用思考指南

> **目的**：动手写新代码前，先确认它是否已经存在。

---

## 核心习惯：先搜索，再修改

```bash
# 修改任何常量、文案或路径前，先全仓库搜索
grep -rn "value_to_change" .

# 找相似实现（按函数名/关键字）
grep -rn "keyword" crates/ web/src/
```

## 何时抽象（本项目准则）

- 重复出现 3 次以上，或多调用方边界明确时再抽象（见 [架构概览](./architecture-overview.md) 的抽象分层）。
- 复用落点固定：跨 crate 领域类型 → `types`；算法后处理工具 → `algo_sdk::cv`；前端共享 UI/工具 → `web/src/components/`、`web/src/lib/`。
- 一次性简单逻辑留在本地，不为复用制造循环依赖。

**不要抽象**：只用到一次、平凡一行、抽象比重复更复杂时。

## 常见重复模式

1. **复制粘贴函数**：把校验/转换提取到共享工具，各调用方 import。
2. **相似组件**：先扩展现有组件（props/variants），而不是再写一个 80% 相似的新组件。
3. **重复常量/映射**：单一真源；枚举取值表与联合类型双向锁定（见 [类型与时间](../web/frontend/type-safety.md)）。
4. **多消费者各写一份载荷解析**：WS/DTO 载荷由数据拥有者导出类型守卫与归一化，消费方只读取（见 [跨层思考指南](./cross-layer-thinking-guide.md)）。
5. **仓储查询转义/关键字模板**：复用 `repository/query.rs` 的共享工具（见 [数据库规范](../db/backend/database-guidelines.md)），不得再抄一份。

## 批量修改之后

1. 复查：同类变更是否全部覆盖；
2. 搜索：grep 确认没有漏网；
3. 判断：这次是否该抽成共享实现。

## 提交前检查清单

- [ ] 搜索过现有相似实现
- [ ] 没有应共享的复制粘贴逻辑
- [ ] 没有共享守卫之外的第二份 payload 解析
- [ ] 常量只有一处定义，改一处全仓库生效
- [ ] 相似模式遵循同一结构
