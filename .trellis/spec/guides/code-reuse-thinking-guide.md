# 代码复用思考指南

> **用途**：写新代码之前先停一下 —— 它是不是已经存在了？

---

## 问题所在

**重复代码是不一致性 bug 的头号来源。**

当你复制粘贴或重写已有逻辑时：

- Bug 修复不会传播到副本
- 行为随时间逐渐分叉
- 代码库越来越难理解

---

## 写新代码之前

### 第一步：先搜索

```bash
# 搜相似的函数名
rg "function_name" .

# 搜相似的逻辑关键词
rg "keyword" .
```

### 第二步：问自己这几个问题

| 问题 | 如果是…… |
|------|---------|
| 已经有类似的函数吗？ | 用它，或扩展它 |
| 这个模式在别处用过吗？ | 遵循已有的模式 |
| 这段逻辑可能被共用吗？ | 放到合适的公共位置 |
| 我是在从另一个文件复制代码吗？ | **停下** —— 抽取到共享位置 |

---

## 常见的重复模式

### 模式 1：复制粘贴函数

**差**：把一个校验函数复制到另一个文件

**好**：抽取到共享模块，需要的地方 import

### 模式 2：相似的组件

**差**：新建一个和已有组件 80% 相似的组件

**好**：给已有组件加 props 或 variant 来扩展

### 模式 3：重复的常量

**差**：同一个常量在多个文件里各定义一份

**好**：单一真相源，其它地方引用

在 Argus 里这类值尤其危险，因为它们跨语言存在：

| 值 | 出现在 |
|----|--------|
| 模型输入尺寸、均值方差 | `models/<name>/manifest.toml`、Rust 预处理、转换脚本 |
| 检测类别表 | `manifest.toml`、Rust 后处理、前端标签与颜色变量 |
| 时间戳单位 | Rust DTO、SQLite schema、TypeScript 类型 |
| API 字段名 | Rust `serde` 派生、TypeScript `types/api.ts` |

**规则**：这些值只允许有一个真相源。改之前先 `rg` 搜一遍全仓库，Rust、C++、TypeScript、TOML 都要搜到。

### 模式 4：重复解构同一份 payload

**差**：多个消费方各自就地断言同样的字段：

```typescript
const label = (msg as { label?: string }).label
const score = (msg as { score?: number }).score
```

哪怕只有两行，这也是重复的契约逻辑。每个消费方现在都有了自己那一版"什么算合法 payload"的定义。

**好**：把解码器、类型守卫或投影放在数据所有者旁边：

```typescript
if (isEventCreated(msg)) {
  onEvent(msg.payload)
}
```

**规则**：同一个未定型的 payload 字段在 2 处以上被读取时，先建共享的类型守卫 / 归一化函数 / 投影，再写第三个读取方。

## 什么时候该抽象

**该抽象**：

- 同样的代码出现 3 次以上
- 逻辑复杂到会藏 bug
- 多个人 / 多个模块可能需要它

**不该抽象**：

- 只用一次
- 一行就能写完的小事
- 抽象本身比重复更复杂

Argus 里的补充判断：**跨 crate 的抽象成本更高**。`types` 里每加一个类型，所有 crate 都要跟着重编译。只被一个 crate 用的东西留在那个 crate 里。

---

## 批量修改之后

当你对多个文件做了相似的修改：

1. **回看**：所有实例都改到了吗？
2. **搜索**：`rg` 一遍，找漏掉的
3. **思考**：这是不是该抽象掉了？

### 状态转移应该有穷尽结构

当状态由 action 类的值（`action`、`kind`、`status`、`phase`）推导时，用一个集中的 `match` / `switch`，而不是散落各处的 `if/else`。

Rust 的 `match` 天然有穷尽检查，这是优势 —— **不要用 `_ =>` 兜底把它浪费掉**：

```rust
// ❌ 通配分支：以后新增变体时编译器不会提醒你
match event.kind {
    EventKind::Motion => { ... }
    _ => { ... }
}

// ✅ 显式列全：新增变体时编译期就会报错
match event.kind {
    EventKind::Motion   => { ... }
    EventKind::Object   => { ... }
    EventKind::Offline  => { ... }
}
```

TypeScript 侧用 `never` 断言达到同样效果，见 [../frontend/type-safety.md](../frontend/type-safety.md)。

**为什么重要**：事件日志是真相源时，这个转移表就是被文档化的重放模型。展示代码和命令不应该各自复制它的一部分。

## 提交前检查清单

- [ ] 搜索过是否已有类似代码
- [ ] 没有本该共享却复制粘贴的逻辑
- [ ] 没有在共享解码器之外重复解构 payload 字段
- [ ] 常量只定义在一处
- [ ] 相似的模式采用相同的结构
- [ ] 状态转移集中在一个 `match` / reducer 里

---

## 陷阱：非穷尽分支的静默错误

**问题**：不做穷尽检查的分支结构（Rust 的 `_ =>`、TypeScript 没有 `never` 断言的 `switch`、Python 的 `if/elif/else`）在新增枚举值时会静默走到兜底分支，返回错误的默认值。

**症状**：新加的东西"部分能用"—— 某些路径返回了默认值而不是新值，**不报任何错**。

**Argus 里的高危场景**：新增一个推理后端或一个检测类别时，仓库里所有按后端名 / 类别名分支的地方都要加显式分支。这些分支点分布在 Rust 后端注册、预处理路径选择、前端标签渲染、颜色变量里。

**预防**：

- Rust 侧尽量用枚举而非字符串，并禁止 `_ =>` 兜底
- 新增枚举值后先 `cargo check`，让编译器帮你找出所有分支点
- 跨语言的（Rust 枚举 ↔ TypeScript 联合类型）编译器帮不上忙，必须手动 `rg` 全仓库

---

## 陷阱：多套机制产出同一份结果

**问题**：当两套不同的机制必须产出相同的东西时，结构性变更只会跟着其中一套走，另一套静默漂移。

**Argus 里的真实对应**：

- **三个推理后端必须产出格式一致的 `Vec<Detection>`**。给 CPU 后端加了新字段却忘了 RKNN 后端，开发机上全绿，上设备就不对
- **模型 `manifest.toml` 与转换脚本**必须描述同一套参数。手动跑了一次转换命令但没改脚本，下次重新转换就是另一个模型
- **预处理的缩放/padding 与后处理的坐标还原**必须互为逆运算。改了一边忘了另一边，表现是"框偏一点点"，肉眼几乎看不出来

**预防**：

- **最好的办法是消除不对称** —— 让两套机制共用同一份定义（例如坐标变换的正逆运算写在同一个模块里，互相引用同一组参数）
- **不对称无法消除时**：加一个对比两者输出的回归测试。跨后端一致性测试就是干这个的，见 [../backend/inference-backends.md](../backend/inference-backends.md)
- 迁移结构时，搜出**所有**引用旧结构的代码路径，别凭记忆

## 复用之前先确认边界

Argus 的 crate 依赖是单向的。抽取共享代码前先确认它该往哪放：

- 两个 crate 都要用 → `types`
- 只是把别人拼起来 → `app`
- 前端两个 feature 都要用 → `src/components/` 或 `src/lib/`

**不要为了复用而制造反向依赖**。宁可重复一小段，也不要让 `media` 依赖 `infer`。依赖方向见 [architecture-overview.md](./architecture-overview.md#crate-依赖方向)。
