# 通用 Linux 网络配置机制与适配方向

状态：技术方案草稿，尚未进行目标设备验证，也不代表所有网络管理后端均已纳入首版。

## 用户目标

从 Heimdall 控制台修改边缘设备实际网卡的 IP，配置真实生效并在设备重启后保持。用户不应先辨认 Linux 发行版才能使用网络设置。

## 通用机制的边界

| 能力 | 通用机制或实际归属 | 设计含义 |
| --- | --- | --- |
| 查询网卡、IP 地址与路由 | Linux rtnetlink；`ip` 命令是其常见用户态工具 | 可以提供统一的实际运行状态查询，不必按 Ubuntu/Debian 等发行版分别定义 API。 |
| 修改当前 IP、前缀和路由 | Linux rtnetlink，可在进程拥有目标网络命名空间所需权限时操作 | 内核修改本身不会建立重启后的持久化配置，也可能被现有网络管理服务重新覆盖。 |
| 重启后保持配置 | NetworkManager、systemd-networkd、ifupdown 等管理服务及其持久化配置源 | Linux 没有一个所有系统共同使用的持久化网络配置文件；需要识别并适配实际所有者。 |
| DHCP | 用户态 DHCP 客户端或网络管理服务 | 不能仅靠设置内核 IP 地址来实现地址租约、续租和恢复。 |
| DNS | 网络管理服务、systemd-resolved 或其他解析配置管理方式 | DNS 不属于 rtnetlink 地址配置；不能无条件覆盖可能由服务管理的 `/etc/resolv.conf`。 |

上述是 Linux 通用机制分析，尚非本仓库已有实现。当前仓库未发现可复用的网卡配置服务。

## 适配原则

1. 前端与 HTTP API 使用统一网络配置模型；网卡列表、当前值、可编辑能力及应用结果由后端返回。
2. 后端按目标网卡识别实际管理服务，不按发行版名称硬编码判断，也不能把“安装了 nmcli”或“某服务正在运行”当成网卡归属的充分证据。
3. 已由网络服务管理的网卡，通过该服务及其持久化配置源完成修改，避免直接用 rtnetlink 写入后又被服务覆盖。
4. NetworkManager 与 systemd-networkd 可作为优先研究的常见适配对象；具体支持的版本、持久化、应用和恢复能力需逐项验证。
5. Netplan 是声明式配置与生成层，可生成 NetworkManager 或 networkd 配置。需要识别源配置，不能仅修改 `/run` 下的生成结果并声称已持久化。
6. 未识别或不受支持的网卡管理方式仍可展示实际运行信息，但应明确缺少的配置能力；不得把仅在内核中临时修改当成完整保存成功。
7. 对没有现成管理服务的网卡，若要由 Heimdall 自行持久化、开机恢复并管理 DHCP/DNS，则涉及接管网卡生命周期，需要单独评估。它不是默认的“通用 fallback”，不能与现有管理服务争用同一网卡。

## 修改管理网卡时的应用流程草案

- 校验输入并保存当前可恢复状态。
- 在当前连接仍可用时返回操作标识与新地址访问指引，再执行网络切换。
- 优先研究网络管理服务提供的检查点或恢复机制；将运行状态与持久化配置的恢复一起考虑。
- 以新地址的可达性和确认结果判断变更是否成功；不能仅凭本地命令退出码或数据库写入成功判断管理员仍可访问。
- 应用失败或确认超时后的恢复行为需在最终设计中定义，并覆盖进程退出、设备重启、并发修改等场景。超时参数与首版保障范围尚未定稿。

## 后续设计与验证

- 明确支持的后端、最低版本及每块网卡的配置归属和能力判定。
- 明确配置源、权限范围、异步应用状态、幂等性、持久化和恢复契约。
- 网络与对时服务属于新出现的宿主系统职责。现有架构约定主要围绕媒体/推理平台隔离，具体模块归属需在 `design.md` 中对齐仓库边界，不能直接把操作系统命令写进 API handler。
- 用隔离 Linux 环境或目标设备验证 IP/路由修改、配置重启保留及断连恢复；不对开发机当前管理网卡做变更实验。
- 当前只完成机制分析和规划修正，没有修改产品代码或运行网络配置命令。
